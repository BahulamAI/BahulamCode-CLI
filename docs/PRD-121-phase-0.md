# PRD-121: protocol and offline replay

Implemented on 2026-11-14. This is the first Phase 0 slice, not a live replacement
for the terminal. The existing Node entry point and UI remain the default.

## Run the prototype

```bash
npm run test:protocol
npm run test:tui
npm run test:tui:roundtrip
npm run tui:replay
# Build and opt into the in-process Rust terminal client:
npm run tui:build
BAHULAM_TUI=rust TARANG_ENV=local node src/terminal/main.mjs
# Pipe-safe output, without taking over the terminal:
npm run tui:replay -- --plain
# Replay an actual session (keep its payloads directory alongside the log):
cargo run --manifest-path rust/Cargo.toml --locked --bin bahulam-tui -- --replay /path/to/events.jsonl
# Follow an active session in a second terminal:
cargo run --manifest-path rust/Cargo.toml --locked --bin bahulam-tui -- --replay /path/to/events.jsonl --watch
```

The replay binary shows transcript cards, agents in first-seen order, a plan,
and usage/status. Up/Down and PageUp/PageDown scroll; Home returns to the top;
q, Esc or Ctrl+C exits. Non-TTY input/output automatically selects plain output.
There is no model call, credential requirement, prompt submission or tool execution.
For a live coding session, start the normal Node CLI with
`BAHULAM_DAEMON_EVENTLOG=1 TARANG_ENV=local node src/terminal/main.mjs`, then
open the resulting `~/.bahulam/sessions/<session-id>/events.jsonl` in another
terminal with `--watch`. Find the newest session directory with
`ls -td ~/.bahulam/sessions/* | head -1`. The Rust viewer refreshes every 250 ms
and colors active, successful, waiting and failed cards. Node retains the prompt
in the first terminal; the Rust window is a live read-only view. Logging must be
enabled before the session starts.

Build prerequisites: Rust/Cargo (tested locally with 1.95.0); Node 18+ for the
producer/schema checks. `rust/Cargo.lock` pins the Rust dependency resolution.
The replay uses [Ratatui](https://docs.rs/ratatui/0.30.2/ratatui/) and
[crossterm](https://docs.rs/crossterm/0.29.0/crossterm/).

## Protocol review decisions

1. **Event identity and tool correlation are separate.** `id` is unique per event,
   minted from session ID and durable sequence. `data.tool_id` is the stable tool
   invocation identifier on its requested/started/output/finished events. Never
   reuse an event ID for multiple events. Existing `call_id`, `_callId`,
   `tool_call_id`, `tool_id`, `request_id`, and `id` source aliases are recognized.
2. **`turn_id` is present in v2, nullable outside a turn.** Session bootstrap uses
   null. The tap preserves explicit turn IDs or assigns a local sequence-based
   ID through the next completion. This is attribution, not core turn control.
3. **Agent runs need run IDs.** `run_id` and `sub_agent_run_id` take precedence over
   agent type/name, so two concurrent reviewers do not share a row. Missing
   attribution gets an explicit `unattributed` identifier rather than silently
   attaching internal tools to the main agent. A future producer change must
   supply IDs where absent; the client must not guess correlations.
4. **One serialized frame feeds disk and v2 subscribers.** Timestamps and IDs
   are not regenerated by the broadcaster. Persistence remains buffered and
   best-effort; being broadcast does not mean fsync has completed.
5. **Large payloads use a session-relative reference.** When serialized `data`
   exceeds 4096 UTF-8 bytes, the complete data object is stored at
   `payloads/event-<seq>.json` with mode 0600. The envelope adds `payload_ref`
   and retains bounded scalar metadata. Replay resolves only paths inside the
   session directory. Unlike the future virtualized client, this spike eagerly
   loads referenced payloads (up to 64 MiB each).
6. **Final message text can accompany its hash.** `message_end.data.text` handles
   providers that send a final response without deltas or revise their streamed
   response. It replaces that message's preview; it is not appended twice.
7. **Existing transports remain v1 during Phase 0.** The event log is v2 behind
   the existing `BAHULAM_DAEMON_EVENTLOG=1` gate. Default broadcaster subscribers
   and socket replay receive v1 compatibility projections of their existing
   event families; new families are omitted to avoid unknown-event spam in old
   attach clients. A subscriber can opt
   into `{ schemaVersion: 2 }`. Live transport negotiation remains Phase 1.
8. **Command schemas do not implement commands.** The named command payloads
   are contract candidates for the later stdio host. That host still needs
   version negotiation, command dispatch and acknowledgements. Canonical new
   commands use `{ type, data }`; legacy socket hello keeps its existing shape.

The source is `src/protocol/session-v2.schema.json`. Run
`npm run protocol:generate` after an intentional schema change. Generated
TypeScript declarations and Rust serde structs are checked by
`npm run protocol:check`; golden fixtures cover every declared event/command.
Envelope readers accept v1/v2 and ignore unknown event types. This contract
candidate still needs the Phase 0 freeze review, especially the live command
semantics, before Phase 1 begins.

| --- | --- | --- |
| Tool calls/results | Uniform status cards, primary argument, duration/exit metadata, first 3 output rows on success, last 20 rows on failure, lazy full-payload loading and a keyboard-accessible `+ Show details` view | Read-only grouping, background tasks, structured JSON/table previews, mouse-click actions |
| Messages | Stream reconstruction, final-text reconciliation, Markdown blocks, basic code coloring and full-message detail view | Incremental parsing, word-level diff, copy actions, measured 50–100 ms coalescing |
| Agents | Stable run attribution, parent-aware and identity-colored rows, status/current tool/tokens/elapsed, keyboard transcript drill-in, speaker-labeled agent messages, hidden internals by default, final report card | Full failure detail, agent-scoped stop/approval, per-agent cost and comprehensive end-of-turn summary |

| Interaction | Opt-in Rust prompt, byte-safe cursor editing, multiline entry, panel focus, once/deny approval keys over stdio | Mouse/selection/clipboard, history/search/editor, palette, complete approval scopes and shortcut parity |
| Renderer | Opt-in Rust full-screen client, semantic themes, responsive layout, bounded visible-card rendering, history on exit | Capability probes and fallbacks, synchronized output, full terminal restoration matrix, rich content and cross-terminal validation |

The guide's original Rust-core assumption is superseded by PRD-121: **Node owns
the core; Rust owns terminal presentation**. The product default is the inline
conversation view, matching the current TypeScript terminal. Full-screen is an
explicit opt-in for users who want the live agent tree and richer session
controls. Keep the current Node terminal as the default until Rust Inline reaches
visual and functional parity. `BAHULAM_TUI=rust` currently selects an
experimental full-screen client: Node owns the REPL, model requests, context,
tools and approvals; the Rust child owns the TTY, draws the view, and sends
prompts/decisions over inherited file descriptors 3 (events into Rust) and 4
(commands back to Node). Build the local binary with `npm run tui:build`. This
is an integration slice, not a claim of full UI parity or production readiness.
While the Rust child runs, Node gives up the terminal completely: the fixed input
dock is unmounted (its scroll region and 1 Hz metadata repaint would otherwise
paint through the alternate screen) and the execution-time raw stdin reader stays
off so the two processes never race for keystrokes. In live mode Esc interrupts
the running turn, one Ctrl+C clears the prompt and interrupts, a second Ctrl+C
within two seconds quits, and Ctrl+Q quits; Esc only exits in replay mode. The
REPL records `turn_started` with the prompt text and a `tool_started` frame per
tool request, since the backend emits neither, so the transcript shows the user's
own message and tool cards move through a running state.
Slash commands use Node's existing dispatcher; while the Rust screen owns the
terminal, their stdout/stderr is captured and returned as a display-only
`command_result` card (capped at 1 MiB) instead of disappearing behind the
screen's terminal-write suppression. The live Rust subscriber receives events
without requiring disk event logging; large display payloads stay in a bounded
process-local detail store and are released when the client disconnects.
Startup resume and `/resume` now send a selected-mode transcript snapshot to
Rust, including ordered replay events where available. Long slash-command
output keeps a compact preview and opens the captured output from the existing
details view. `/models` aliases the canonical Node `/model list` handler. Rust
also supplies keyboard-driven pickers for resume, model role/model selection,
login confirmation and session approval grants; command behavior still runs in
the TypeScript REPL. Command completion is supplied by the TypeScript command
catalog. `/clear`, `/new`, resume and model changes refresh Rust view state.
In the full-screen view, Tab focuses the agent panel, Up/Down selects an agent,
and Enter opens that agent's transcript. Ctrl+N/P navigates only that transcript's
cards; Enter opens the selected tool's complete details, and Esc returns to the
main conversation.

The integrated prototype does not yet meet the complete production UI guide.
It now has a deliberate visual system (semantic dark/light/high-contrast/ANSI
themes, responsive panel layout, focused borders, concise status cards, formatted
Markdown/code previews, a pinned multiline prompt, and an approval panel), but
still lacks synchronized-output capability probing, mouse selection/clicks,
clipboard, terminal capability fallbacks, core output sanitization and
credential redaction, rich-item registration, image/diagram rendering, and
Windows terminal support. Display control sequences are made inert by the
renderer; that is not a replacement for planned core sanitization before
logging/model consumption. Visible rendering is bounded to the viewport, while
the event model still retains the session transcript in memory and does not
claim the Phase 2 1,000-tool-call memory target. The full cross-platform stdio
host and terminal matrix are outstanding.

## Validation and remaining gates

### Context and cache preservation

The Phase 0 audit found no prompt-cache invalidation introduced by the event
protocol changes in the tested paths. Context construction, memory snapshots,
history reduction and provider request builders remain unchanged. Display logs
are not the source of model history. The tap serializes a separate object before
publishing it, so subscriber edits cannot change canonical tool arguments.

`test/test-protocol-cache-invariance.mjs` compares exact serialized request bodies
with logging disabled, enabled, and enabled again after advancing log IDs and
reading replay data. It exercises the real request builders for `/api/execute`,
the gateway, direct Anthropic, OpenRouter Anthropic and OpenRouter automatic-cache
models, with HTTP mocked locally. It verifies full `llm_content` survives display
payload offload, tool/message ordering is unchanged, a mutating display subscriber
cannot affect inputs, and existing cache breakpoints remain intact. It is included
in `npm run test:protocol` and the unit suite.

This is local request-equivalence evidence, not a measurement of provider cache
hits, TTL expiry, routing or production cost. The backend's subsequent prompt
assembly and the integrated Rust host need validation before rollout. The request
body invariance test covers the Node producer; it does not validate visual state.

Keep these risks as explicit live-client gates:

- Never inject event timestamps, sequence IDs, UI state, usage counters or display
  formatting into model context or the static prompt prefix.
- Preserve canonical tool results and call IDs. Preview truncation, grouping,
  escaping and `payload_ref` belong to the display path; replay cards must not
  replace the model's structured history on resume.
- Preserve tool-schema order, memory digests and cache marker placement. Real
  instruction/tool/memory changes legitimately change context; terminal redraws,
  attach/detach and capability probing must not.
- Measure logging overhead separately. Large display payloads currently use
  synchronous sidecar writes; this can add latency even with identical prompts.
  Phase 0 does not establish live throughput or timing guarantees.

Automated local coverage includes schema generation drift, every event/command
fixture, v1 replay, v2 IDs, live/log equivalence, payload offload, sequence recovery
after a stale checkpoint/torn tail/rotation, call-ID and agent-run attribution,
existing daemon socket/attach/approval regression tests, Rust cell-buffer checks
at 120×36, 80×24, 40×16 and 1×1, and a real Node-producer-to-Rust-consumer round trip.
CI adds Rust replay checks on Linux, macOS and Windows; these jobs are configured,
not yet observed running remotely.
